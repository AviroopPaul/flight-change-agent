1. Where each part runs

Three hosts. The browser holds no secret: it gets a short-lived LiveKit room token from the backend.

2. One session, two channels

Both channels are clients of one engine. Every change goes through apply: lock the row, run a pure command, decide the outcome, write events, commit.

3. A spoken answer

Latency is end of speech → first agent audio: end-of-utterance delay + LLM first token + TTS first byte (p50 0.80 + 0.50 + 0.34 s).

4. A chat answer during a call

The call agent learns about typed answers at once, and asks nothing new while a chat box is open.

5. What is collected, in order

One input at a time on both channels. Each card waits until it is answered (the optional email too: type it or tap Skip).

9. Key decisions

Backend owns all state

The agent and the page are thin clients. One Postgres row per session, changed only by the engine.

Pure engine

Commands are pure functions of (state, input, now), so outcome rules are unit tested without I/O.

Event log as the chat

The chat is a replay of events with ids, so a reload or reconnect shows the same thread with no duplicates.

Typed wins for letters and digits

STT mangles PNRs and names. Spoken values are hints; the chat value wins and the conflict is logged.

One input at a time

One open card. The call agent waits for it and asks no new spoken question until it is submitted.

LiveKit for voice

WebRTC, barge-in, turn detection and reconnects come built in. The agent is hosted on LiveKit Cloud.

Gemini Flash-Lite on Vertex

Cheapest model with fast tool calls (~0.5 s first token). Service-account key with only the Vertex AI User role.

Outbox for exactly once

Record and state commit together. Delivery retries with an idempotency key, so a restart never sends twice.

The agent never books

It collects, validates, quotes and gets consent. A downstream service would execute the change.
